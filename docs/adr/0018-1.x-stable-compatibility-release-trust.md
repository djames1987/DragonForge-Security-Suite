# ADR 0018 — DragonForge 1.x Stable Compatibility and Release Trust

## Status

Accepted for Phase 25.

## Context

Phase 24 qualified the repository to enter the first stable release. Phase 25 must establish what “stable 1.x” means without weakening the existing cryptographic, IPC, privileged-service, update, and release boundaries.

## Decision

DragonForge 1.x treats the documented 1.0 format/protocol versions as stable compatibility baselines.

Incompatible changes require an explicit new major/format/schema version plus a documented migration path. Existing version numbers must never be silently reinterpreted.

Stable releases are immutable GitHub releases built from an exact tag/commit with tracked locked dependencies. Stable Windows artifacts require Authenticode and RFC 3161 timestamp verification. Stable update metadata requires the pinned ML-DSA-65 update identity and must continue to enforce channel, downgrade, artifact hash/size, and Authenticode requirements.

The normal DragonForge Agent remains per-user and non-elevated. Optional privileged firewall mutation remains isolated behind the typed authenticated/publisher-pinned privileged service. A 1.x release must not expand that into generic elevated execution without a new security review and explicit compatibility decision.

## Release authority

The repository can establish release readiness, but it cannot manufacture production signing identity. Final `v1.0.0` release status therefore requires evidence from the protected signing environment and the immutable published release.

## Consequences

- 1.x users receive a concrete compatibility promise rather than a best-effort convention.
- unknown future formats/protocols remain fail-closed where currently required;
- signing/update credentials remain external to Git;
- release publication remains a separate, auditable trust event;
- future feature work must respect the 1.x compatibility contract or intentionally version/migrate it.
