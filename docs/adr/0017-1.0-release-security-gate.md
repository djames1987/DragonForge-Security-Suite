# ADR 0017 — 1.0 Release Security Gate and Feature Freeze

## Status

Accepted for Phase 24.

## Context

DragonForge has accumulated independently verified security, recovery, update, privilege, automation, and accessibility phases. Before 1.0, the project needs one release decision that composes those guarantees and prevents feature work from expanding the attack surface during final qualification.

## Decision

Phase 24 establishes a feature freeze and one authoritative release-audit verifier.

The gate requires:

- a clean exact Git working tree;
- locked Cargo dependency metadata;
- formatting, full workspace compile, strict Clippy, tests, and doc-tests;
- live RustSec advisory review;
- locked dependency license inventory;
- deterministic same-commit source archive reproduction;
- tracked-source secret-material scan;
- deterministic malformed-input mutation regressions;
- fail-closed privileged-service, update, installer, and release-publication invariants;
- complete Windows suite application build.

Phase 24 does not publish the stable release. Phase 25 owns the actual stable tag, signed artifacts, signed update metadata, and publication.

## Feature freeze

The 1.0 component set, encrypted formats, IPC/protocol semantics, privileged capability set, and update trust model are frozen after Phase 24 unless a release-blocking security or correctness issue requires a reviewed exception.

## Reproducibility

DragonForge claims deterministic reproduction of a Git source archive for the same commit.

DragonForge does not claim bit-for-bit Windows binary reproducibility across toolchains or signing timestamps. Stable release trust instead depends on exact tag/commit identity, tracked lockfiles, artifact SHA-256 manifests, Authenticode with timestamp verification, and signed update manifests.

## Dependency licensing

A new dependency license identifier is fail-closed until explicitly reviewed and added to the Phase 24 allowlist. This prevents an unnoticed licensing change from silently entering the stable release.

## Residual risk

The release decision must preserve a written residual-risk register. Accepted limitations are not silently converted into security claims.

## Consequences

- Phase 25 begins from a frozen, auditable source baseline.
- security/release invariants become machine-verifiable;
- new feature work is deferred until after 1.0;
- release audit failures block stable publication rather than being advisory.
